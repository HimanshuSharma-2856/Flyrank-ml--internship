# Week 6 - Agents and MCP

## Workflow versus agent

Anthropic’s distinction is useful because it separates the shape of a system from the amount of
marketing language around it. A **workflow** has a path designed in advance. The builder decides
which prompt runs first, what output is handed to the next step, where a check happens, and when the
process ends. An LLM may make local choices inside a step, but the overall route is prescribed.

An **agent** starts with a goal and is allowed to decide more of the route while it works. It can
choose which tool to call, inspect the result, change its plan, recover from an error, ask for
missing information, and stop when a completion condition is met. In a reliable agent, the model
does not operate on imagination alone: it repeatedly gets ground truth from its environment through
tool results or code execution. That flexibility costs more latency, money, testing, and control.

My FL-04 build is a **workflow**, specifically a prompt-chaining evaluator-and-revision workflow.
Its route is fixed: intake and source lock, evidence-grounded draft, skeptical critique, human
decision and revision, then submission formatting. The human is the decision-maker at the revision
gate. The workflow does not choose a new research path, discover an arbitrary next tool, or loop
until it believes the work is finished. That predictability is a feature here because the writing
has a known rubric and a high cost for unsupported claims.

## What MCP adds

The Model Context Protocol is an open standard for connecting an AI application to external systems.
The useful analogy is a common connector shape: an AI client can discover and use compatible servers
without every integration inventing a different interface. MCP does not make a model an agent by
itself. It supplies an interface through which a workflow or an agent can obtain context or take an
action.

MCP exposes three important primitives:

- **Tools** are callable operations. A tool can read a file, query a database, search a service,
  run code, or perform an approved action. The model receives a typed description and arguments,
  and the client returns the tool result.
- **Resources** are addressable context, such as a document, repository file, database record, or
  other data source. They let the client or user make information available without pretending it
  was generated by the model.
- **Prompts** are reusable prompt templates exposed by a server. They package a useful interaction
  pattern, but they are still instructions, not autonomous behavior.

The distinction matters in practice. A tool call can prove that a file exists or that a syntax check
passed; plain chat can only suggest that this may be true. MCP also makes permissions and boundaries
more visible: the client can show which server and operation were used, while the server can limit
what the operation is allowed to do.

## Connector evidence from this session

I connected to the available **Pylance MCP server** through this VS Code MCP client. The following
three tasks required an external tool rather than ordinary chat:

1. `pylanceWorkspaceRoots` returned the repository workspace root:
   `vscode-vfs://github/HimanshuSharma-2856/Flyrank-ml--internship`.
2. `pylanceSettings` returned the effective Python/Pylance analysis configuration, including the
   diagnostic mode, indexing settings, type-checking mode, and package index depths.
3. `pylanceSyntaxErrors` checked a Python snippet that reads the workflow document and asserts that
   the five-run section exists. The tool returned: **“No syntax errors found in the code snippet.”**

These are tool results, not generated claims. A submission screenshot should show the three MCP
tool calls and their returned results in the client transcript. The attempted `pylanceRunCodeSnippet`
task also exposed a useful failure: it returned **“Python path is not set in the workspace
configuration.”** I therefore do not claim that code execution succeeded. That is exactly the kind
of environment fact a connector can reveal and ordinary chat cannot verify.

## What would make FL-04 an agent?

The concrete upgrade would be a **source-audit agent** around the existing workflow. I would give it
read-only tools to list approved repository files, open a selected notebook, run its validation in a
sandbox, search for private identifiers, and inspect the resulting metrics. Starting from a new
artifact request, the model could decide whether it needs the data-contract notebook, the leakage
check, or the claim-writing notes; run the smallest relevant checks; revise its critique after seeing
the results; and stop at a human approval checkpoint. A maximum tool-call count and a no-write
default would limit cost and risk.

That would add useful flexibility, but I would not remove the fixed human gate. The agent could
gather evidence and propose a revision, while I would still decide whether the research question,
privacy boundary, interpretation, and public claim are acceptable. The upgrade is justified only if
different inputs genuinely require different evidence paths. Until then, the simpler workflow is
more transparent, easier to test, and less likely to compound a polished mistake.
